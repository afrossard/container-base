# Shipped-dependency bumps are `fix:`, everything else stays `chore(deps)`, and semantic commits are explicit

Issue #92 found `renovate.json` producing PR titles release-please's commit parser rejects outright: #85, #89, and #91 all landed as bare descriptions ("Update googleapis/release-please-action action to v5"), no Conventional Commits prefix, so merging them contributed nothing to the next release - no version bump, no CHANGELOG entry, silently dropped.
The suspect was `semanticCommits: "auto"` (inherited from `config:recommended`, never set explicitly), which is supposed to detect Conventional Commits usage and prefix titles accordingly.

Driven for real, not assumed: `renovate`'s own `detectSemanticCommits()` resolves `"auto"` once per repository run by taking the last 20 commit subjects (`git log -n 20 --format=%s`) and running them through the bundled `conventional-commits-detector` package, which scores each subject against a handful of hardcoded regexes (`angular`, `atom`, `ember`, `eslint`, `jquery`, `jshint`) and returns whichever convention matched the most lines; `"auto"` becomes `"enabled"` only if `angular` wins, and `"disabled"` otherwise - a plurality vote, not a threshold, over a 20-commit sliding window, re-run fresh every scan.
Extracting this exact library (`conventional-commits-detector@2.1.1`, as pinned by the installed `renovate@37.440.7`) and feeding it this repo's real commit subjects confirmed the mechanism: run against `main`'s last 20 subjects as of the commit immediately before #89 merged, it already returned `angular` (4 Conventional Commits subjects beat 0 for every other convention) - yet #89's actual title carried no prefix.
The two facts only reconcile one way: Renovate doesn't retitle an already-open PR each run, so whichever scan first opened a branch decided its title for good, and #85/#89/#91 were all first opened during the mixed transition window ADR-0018 itself describes (the batch of pre-ADR-0018, unprefixed commits around release PR #90), when the trailing 20-commit window their opening scan saw was mostly non-conventional.
`"auto"` is therefore not merely history-dependent, it's scan-timing-dependent: a dependency PR's title is decided once, by whatever 20 commits happened to be on `main` at that specific moment, and low commit velocity or a run of Renovate's own past unprefixed titles can push the window back to `disabled` again later even after this repo's Conventional Commits adoption is well-established.

We decided to set `"semanticCommits": "enabled"` explicitly in `renovate.json`, removing the detection step entirely: `renovate`'s `compileCommitMessage()` only semantic-prefixes a title when `upgrade.semanticCommits === 'enabled'` exactly, a value explicit config supplies unconditionally, with no dependency on git history or scan timing.

Issue #92's first question - whether a Renovate PR should ever count as `fix:` - turned out to have a real answer, not the "nothing ships" non-answer an earlier draft of this ADR gave before catching its own mistake in review: `config:recommended` extends `:semanticPrefixFixDepsChoreOthers`, which sets `semanticCommitType: "chore"` for every dependency except ones whose `depType` is `dependencies` or `require`, and none of the managers this repo runs ever assigns that `depType` - `dockerfile` tags stages `stage`/`final`/`syntax`, `github-actions` tags actions `action`, `npm` tags this repo's tooling manifest `devDependencies`.
Left alone, every Renovate PR would resolve to `chore(deps)` regardless of what it touches.
But `images/dev/Containerfile` and `images/dev/devcontainer.json` are exactly what CONTEXT.md's shipped-dependency entry describes: `debian:trixie-slim` is the dev image's base, `COPY --from=ghcr.io/astral-sh/uv:0.12.3` bakes the `uv`/`uvx` binaries in directly, and the `common-utils` devcontainer feature is applied into the built image, not just declared - all three are third-party artifacts baked into the published `-dev` tag, so a Renovate bump to any of them changes what a consumer pulls, the exact shape of gap issue #75 found and ADR-0018 was written to close.
`images/agent/devcontainer.json`'s `docker-in-docker` feature is the same case for the `-agent` tag; `images/agent/Containerfile`'s own `BASE_VERSION` pin is not Renovate's to bump at all (ADR-0018 moved it to release-please), so no packageRule is needed there.
`.devcontainer/Containerfile` (this repo's own workspace image, explicitly out of scope per the issue) and `package.json`'s npm tooling stay `chore(deps)` correctly, because neither ships to a consumer.

So `renovate.json` gains a `packageRules` entry: `matchFileNames: ["images/dev/**", "images/agent/**"]` sets `semanticCommitType: "fix"` for anything Renovate finds under either directory.
Driven for real again, not assumed: `matchFileNames`'s matcher (`util/package-rules/files.js`) runs `minimatch` against each dependency's `packageFile`, and running that exact `minimatch` against this repo's real paths confirms the glob does what's intended - `images/dev/Containerfile` and `images/dev/devcontainer.json` match `images/dev/**`, `images/agent/Containerfile` matches `images/agent/**`, and `.devcontainer/Containerfile`/`package.json` match neither.
A shipped-dependency bump this way always resolves to `fix:` regardless of whether the underlying change is itself patch, minor, or major-sized - the same coarseness `:semanticPrefixFixDepsChoreOthers` already applies to ordinary runtime dependencies, extended to cover images that ship without a `dependencies`/`require` `depType` to hang it on.

Issue #92's third question - whether a Renovate bump riding unreleased until the next human-authored release is intended - now has different answers for the two buckets.
A `chore(deps)` tooling bump riding along indefinitely is fine, because nothing about it is externally observable.
A `fix(deps)` shipped-dependency bump is never silent: it always computes a patch release on its own, the same way a human-authored `fix:` would, so there's no unreleased-indefinitely case left to worry about for the class of bump issue #75 actually cared about.

## Considered options

- **Leave `semanticCommits` on `"auto"` and wait for the commit history to dilute in Renovate's favor.** Rejected: the detector re-runs the same plurality vote on every scan, so an already-open PR's title never self-heals, and a quiet period can regress a later scan's window back to `disabled` even after this repo is dense with Conventional Commits.
- **Treat every Renovate PR as `chore(deps)`, full stop.** This was this ADR's own first answer, and issue #92's own review caught it: it's contradicted by `images/dev/Containerfile`'s `uv` `COPY --from` pin and base image, which are shipped-dependency bumps by CONTEXT.md's own definition, not tooling.
- **Set `semanticCommitType`/`semanticCommitScope` explicitly at the top level instead of via `packageRules`.** Rejected: that would apply uniformly, losing the shipped/tooling distinction the two directories actually need; a single `matchFileNames` rule keeps `config:recommended`'s sane tooling defaults and only overrides the two paths that ship.

## Consequences

- **`renovate.json` gains two things**: `"semanticCommits": "enabled"`, and one `packageRules` entry scoping `semanticCommitType: "fix"` to `images/dev/**` and `images/agent/**`.
- **Every Renovate PR title is now Conventional-Commits-prefixed**, satisfying `pr-title-lint.yml` (issue #96): `fix(deps): ...` for anything touching a shipped image, `chore(deps): ...` for everything else (GitHub Actions, npm tooling, `.devcontainer/Containerfile`).
- **A shipped-image bump always computes a release**, closing the exact gap issue #75 found for hand-authored changes, now also for Renovate-authored ones.
- **A dependency that starts shipping outside `images/dev/**`/`images/agent/**` needs its path added to this `packageRules` entry**, or it silently falls back to `chore(deps)` - this rule is path-scoped, not content-aware, so it doesn't generalize automatically.
- **`CONTRIBUTING.md` gets a short pointer to this ADR** next to its Conventional Commits table, using the "shipped dependency" term CONTEXT.md already defines rather than re-describing the concept in different words.
