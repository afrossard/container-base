# The agent runtime ships as a published image variant

ADR-0011 rejected a second published image on the grounds that the safety-critical controls are launch-time properties an image cannot grant itself, so a hardened image buys almost nothing.
That argument is sound and it does not cover this artifact, because it is about **policy** - firewalls, capabilities, `no-new-privileges` - and the agent runtime differs from the dev image in **carried capability**: it holds a docker daemon, an init or supervisor to run that daemon alongside the agent, and the agent CLI, and it carries no editor server.

We publish it as a third variant, `{version}-agent`, alongside `-dev` and `{language variant}-prod`, from the same GHCR pipeline that publishes the dev image today.

Two things make this the cheap answer rather than a new axis of work.
ADR-0013 defines the reusable, never-written-by-a-session part of an agent runtime as a prebuilt image, which is a published artifact by construction - and publishing shared container images is the entire scope of this repo (ADR-0001).
And a per-container-VM tool that consumes OCI images boots one directly as a VM guest, so `docker build` → GHCR → run-as-a-VM needs no VM-image format, no disk-image publishing, and no second pipeline.

## Consequences

- **ADR-0004's asymmetric tag scheme absorbs this without combinatorics.** `agent` is unqualified by language, exactly like `dev`; only runtime bases keep the language axis. Adding a language still adds one runtime base and nothing else.
- **`CONTEXT.md`'s image-tag entry gains a variant**, and the publish workflow gains one build, not a new package.
- **The agent never needs registry-push credentials.** It builds and tests images; CI publishes them, as it does today.
- **ADR-0011 narrows rather than reverses.** Its conclusion - that hardening is composed by whoever launches, and the image ships enabling machinery rather than active policy - is unchanged and applies to the agent runtime image too.
- **Whether this image is published from this repo long-term is still open.** It is an image, and images are what this repo publishes, which is the argument for keeping it here; if the runtime grows parts that are not image-shaped, that argument weakens.
- **`scripts/launch-agent-runtime` is a deliberate, noted exception to ADR-0001's scope.** The image is what this repo publishes; launching it as a microsandbox guest - the disk-backed `/var/lib/docker` volume, `--secret` credential injection (`docs/research/0022`) - is host-side tooling that consumes the image rather than an image itself. It lives here anyway, next to the artifact it launches, rather than in a separate repo: it has no independent reason to exist, and splitting it out would just add a repo boundary between a script and its one caller for no isolation or reuse benefit. If it ever grows features unrelated to launching this repo's own image, that argument weakens the same way the previous consequence already flags for the image itself. The image itself still has no default command - a missing command run directly against it is a usage error, not a fallback to a standing process; the launcher, one level up, supplies its own default (an interactive shell with a real tty) when a human runs it bare, matching plain `docker run -it`'s convention rather than the image's own stricter rule.
- **The docker daemon is installed by the community `docker-in-docker` devcontainer feature, not hand-rolled apt/gpg steps.** It is the established tool for exactly this shape of problem - a container that needs a full engine of its own - and already carries the fiddly, easy-to-get-wrong parts (moby/docker-ce package selection, cgroup v2 nesting, iptables-legacy/nft alternative selection, containerd wiring) as maintained, Renovate-tracked code (`images/agent/devcontainer-lock.json`), the same mechanism `images/dev` already uses for `common-utils`. `images/agent/Containerfile` only adds `tini`, which the feature doesn't carry.
- **The given command drops to a non-root user via `runuser` inside the entrypoint, not via devcontainer.json's `remoteUser`/`containerUser`.** Verified by experiment, not assumed: `devcontainer build` unconditionally resets the final image's `USER` to root once any feature is applied, regardless of what `containerUser`/`remoteUser` declare or what the base Containerfile's own final `USER` instruction says - confirmed by inspecting the CLI's own generated Dockerfile template and the built image's `Config.User` directly. `remoteUser`/`containerUser` are `devcontainer up`/editor-attach concepts with no effect on a plain `devcontainer build` image; dockerd itself must run as root, so the entrypoint starts it as root via the feature's own `docker-init.sh`, then hands the given command to `runuser -u vscode` once the daemon is up - vscode reaches the docker socket because the feature already added it to the `docker` group at build time.
- **`docker-init.sh`'s cgroup v2 nesting step is noisy specifically under a microsandbox guest, traced (`sh -x`) to the exact line rather than guessed.** It is vendored from Moby's own `hack/dind` and moves every PID already in the root cgroup into a child cgroup, one `xargs`-driven `echo` write per PID; Moby's own comment already calls a failed move "ignored" (the exit code is `|| :`-masked upstream), but the write failure itself still prints. Under a real nested container that list is just the container's own 1-2 processes, so it succeeds silently; under an msb guest, the root cgroup also holds msb's own supervisor processes, most of which legitimately can't move, printing dozens of harmless `echo: write error: Invalid argument` lines. No upstream fix exists for the noise (only for the already-handled exit code), so the entrypoint gives `docker-init.sh` a `true` placeholder instead of the real command, letting it complete its setup and confirm dockerd is up before filtering that one known line out of its stderr and exec'ing the real command via `runuser`.
