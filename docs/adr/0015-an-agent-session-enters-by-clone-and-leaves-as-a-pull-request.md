# An agent session enters by clone and leaves as a pull request

ADR-0013 recorded "the workspace enters by clone and leaves as a branch or PR" as the assumption in force rather than a settled decision.
This settles it, and adds the part ADR-0013 did not cover: what credential makes the "leaves" half possible, and what stops that credential reaching further than the session should.

An agent session's workspace is a **full clone**, made inside the agent runtime at launch, of one repo's public remote.
Work leaves as a branch pushed to that remote and a pull request opened against it.
The session's credential is a **fine-grained personal access token scoped to that one repository**, injected via microsandbox's `--secret` placeholder mechanism so the guest never holds its real value, and `main` is protected by a server-side ruleset because no token can express "push, but not to `main`".

## Considered options

- **Bind-mounting the human's checkout.** Rejected, and the reason is stronger than ADR-0013 states. ADR-0013 argued from `.git/hooks`, but this repo sets `core.hooksPath` to `.husky/_`, a path in the **working tree** - so even a mount that deliberately excludes `.git` hands over host command execution on the human's next commit. `.git` is not where the interesting targets are anyway: `.devcontainer/devcontainer.json`'s `initializeCommand` is documented to run on the host machine, `.claude/settings.local.json` defines hook commands and is gitignored so it appears in no diff, and `package.json` scripts and `node_modules/.bin/` are executed by ordinary developer habit. A writable shared path converts the hypervisor boundary into one that holds only until the human next touches the repo.
- **Bind-mounting a dedicated `git worktree`.** Rejected, and worse than the plain checkout - verified directly rather than reasoned about. From inside a worktree, `git rev-parse --git-path hooks` resolves to the **main** checkout's `.git/hooks`, and the worktree's `.git` is a small file holding an absolute host path. That leaves no good configuration: mount only the worktree and the pointer dangles, so git is unusable in the guest; mount the common directory too and the primary checkout's hooks, refs, object store, and `.git/config` all cross the boundary - and `config` is itself an execution channel, since `core.pager`, `core.sshCommand`, `diff.external`, `filter.*.clean`, and `alias.*` are command strings the host's git runs.
- **Copying the host working tree in** (`msb run --copy-dir`, one-way and pre-boot, so it carries none of the above risk). Rejected on reproducibility rather than safety: the session's starting state would be an unnamed, unreproducible working tree, so a session that produced something good could not say what it started from. Recorded as the escape hatch to reach for if push-before-launch friction proves intolerable in practice - it is the right answer to that friction, and a bind mount is not.
- **Cloning at an explicit ref.** Rejected as invented complexity. A full clone already carries every pushed ref, so checking one out is a single command with a human at the keyboard, while a `--ref` flag useful enough to want would default to the host's current branch and fail at boot whenever that branch is unpushed.
- **No credential in the guest at all**, with `msb copy` out and the human pushing from the host. Genuinely attractive - it is the only option where the guest holds no write access to anything the operator owns - but rejected because an agent that cannot open its own pull request, comment, or file an issue is missing most of what makes an autonomous session worth launching.
- **A GitHub App with per-launch installation tokens.** Deferred, not rejected. Its advantages - one-hour expiry, per-launch permission narrowing, `<app>[bot]` attribution distinguishable in `git log` - are advantages in short, scripted, unattended runs. Its costs land hardest on long attended ones: GitHub ships no supported local minting tool (`gh api` has no JWT or App auth; `actions/create-github-app-token` is CI-only), and the one-hour ceiling would expire mid-session, with the failure surfacing on the final push after all the work. It is the recorded destination for when the headless shape is built.

## Consequences

- **A shallow clone is not an option.** `git merge-base` backs this repo's own `/code-review` skill, and history is what an agent reads to understand a change. The clone is full.
- **The launcher composes the clone, not the image.** ADR-0011's rule is that the image ships enabling machinery while the launcher composes policy, and "which repo, at which path" is policy. It also keeps a clone failure from becoming a boot failure for an image other consumers may launch differently.
- **Cloning needs no credential, and that is load-bearing.** Both this repo and the operator's `dotfiles` are public. A repo-scoped token could not clone a private `dotfiles`, so the moment either repo goes private the credential model needs revisiting, not just widening.
- **The credential boundary is made to coincide with the runtime boundary.** `CONTEXT.md` defines the agent runtime as holding one repo and nothing else; a credential reaching further would mean the runtime's real boundary is larger than its stated one.
- **A ruleset on `main`, not classic branch protection.** Classic protection exempts administrators by default, and a fine-grained PAT acts as the repo owner - so the obvious configuration would be a no-op against precisely the actor it is meant to constrain. Required approvals must be 0: the agent's pull requests are authored by the owner, and GitHub forbids approving your own, so any approval requirement would deadlock every agent PR.
- **The review checkpoint is the diff, and it is the only one.** Checking the agent's branch out on the host carries the same deferred-execution hazard the bind mount does - `.husky/`, `devcontainer.json`, and `package.json` are all tracked. The mitigation is reading the diff before anything executes, which a pushed branch permits and a live mount does not.
- **Reviewing before publication is possible without a mount.** `msb copy` pulls the guest's tree to a host scratch directory, one-way, on demand - which serves "read it before it is public" better than a pushed branch does, since this repo is public.
- **One transport question is open and gates the push half.** microsandbox substitutes a secret in-flight for traffic to the host it is scoped to. `gh` sends its token as a plaintext header and should be unaffected; `git push` over HTTPS uses Basic authentication, which base64-encodes the credential before it reaches the wire, and a byte-string substitution would not find the placeholder there. If that proves true, the push half needs a different transport - an SSH deploy key, which is real key material resident in guest storage and a genuine departure from the placeholder model.
